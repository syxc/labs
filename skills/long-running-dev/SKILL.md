# 把「做完没」说清楚

AI 自动干活，最容易翻车的地方：**做完了不知道对不对**。

不是忘了要做什么，是不知道这一步、这个任务到底算不算完成。靠「应该没问题」「我改的应该没错」往下走——就把别处改坏了，或者一直在原地打转。

## 核心就一句

**做任何事之前，先想清楚：这件事做完没，拿什么证明？**

想不出来，就先别动手。想得出来，做完就拿那个证明去对一下。

## 「做完」长什么样

一个能用的「完成标准」，得能回答这几样（不用全写，缺哪补哪）：

- **做完什么样**：一句话，做成之后世界变成什么样（不是「优化性能」，是「P99 < 200ms」）
- **拿什么证明**：测试、benchmark、截屏、命令输出……具体到一条命令、一个数、一张图。「看着差不多」不算
- **不能改坏什么**：哪些东西动之前是好的，做完还得是好的（已有的测试、已有的功能）
- **只能动什么**：哪些文件、目录、资源在这个任务范围内——越界的东西不碰，防止顺手改坏别处
- **做不下去了怎么办**：卡住的时候，别死磕、别空转——带着「试过什么、卡在哪、下一步要什么」停下来问

## 怎么确认

按可靠程度排，从最可靠往下用：

1. **能跑的**（最可靠）：测试、编译、lint。电脑直接告诉你对错，没含糊。
2. **能看的**：改前端开浏览器看效果，改 UI 截屏对比。眼见为实。
3. **能读的**：出错就把报错完整读一遍，改完看 diff 确认只动了该动的。

**最糟的是靠猜。** 「这应该能跑」「我改的应该没错」——在长程任务里，这种话就是定时炸弹。

## 什么时候用

- 任何要自动推进、自己跑很久的任务：先把完成标准定下来，否则就是让它瞎跑
- 一次改动看起来简单，但牵连很多的地方：先定怎么算改完，再动
- 不确定一个任务到底要做什么的时候：试着写下完成标准，写不出来说明需求还没清楚，先问
